# Rebuild EKA's general FEP with the missing SDK interface

This recipe builds `avkonfep_general.dll` from an explicit EKA checkout with the
0028 cancel patch applied. It stages the source and official SDK interface in a
fresh work directory. It does not launch EKA, deploy assets or modify SDK/EKA
inputs. The HLE guest source remains owned by EKA and retains its GPL headers;
the official header/DEF and accompanying license remain EPL-1.0.

## Inputs and commands

Use the Symbian 0.3.0 SDK and the native converter with patches 0001–0006.
`build-symbian-native.sh` applies those patches and runs the registered native
E32 tests by default. Set the normal SDK/build locations for your machine:

```sh
export SYMBIAN_SDK_PREFIX=/path/to/symbian-sdk
export WORK=/path/to/build-root
SYMBIAN_WEBKIT_WORK="$WORK" SYMBIAN_NATIVE_BUILD="$WORK/symbian-native" \
  bash Tools/Symbian/scripts/build-symbian-native.sh

python3 Tools/Symbian/eka2l1/fep/build.py \
  --eka-source /path/to/patched-EKA2L1 \
  --converter "$WORK/symbian-native/cpp/symbian/tools/symbian-native"
```

The output directory defaults to `$WORK/fep-native`. It must be fresh and outside
the SDK/EKA source trees; `--work`, `--sdk`, `--converter` and `--jobs` override
individual settings. `SYMBIAN_NATIVE` can provide the converter path.
`--prepare-only` copies and verifies inputs without invoking any compiler,
converter, CMake or Ninja. Use a different fresh work directory for a later build.

The build uses the actual EKA `HostBridgedImeFEP.cpp/.h`, dispatch and priv Log
sources, checks the general plugin's MMP identity and rejects source without the
0028 cancel completion entry. Inputs and generated source hashes are retained.
An ARM function type/size annotation and local assembly include path are added
to the copied dispatch; HLE calls and source code are preserved.

The exact official `fepitfr.h` and full frozen `FEPBASU.DEF` are vendored with
`official/sources.json` recording repository, revision, path, Git blob and SHA256.
A proxy containing all present ordinals is generated by the SDK native tool;
there is no replacement OS implementation. Existing native headers/proxies,
startup, leaves and runtime helpers provide the rest of the link.

The FEP explicitly requests ECom UID2 `0x10009d8d`, UID3 `0x100056de`, capability
zero and export ordinal 1 `ImplementationGroupProxy(TInt&)`. The launcher passes
that identity to the native converter before conversion. There is no later E32
header rewriting. Internal EHABI linker labels are hidden while their sections
and relocations remain. The broad Avkon facility's unrelated generated-resource
limitations are not changed by this recipe.

## Outputs and deployment

A completed build writes the DLL, original ARM ELF and GNU ARM `.elf.map` under
`build/`, plus result identities, compile commands and complete tool logs. This
map is a linker map. The plugin keeps the existing UID/ordinal contract and uses
the existing EKA avkonfep override without an extra ordinal remap.

Deployment belongs to the operator: use the matching 0028 host callback, stop all
guests, preserve the previous DLL, copy the newly verified DLL to
`EKA_BUILD/bin/patch/avkonfep_general.dll`, and verify its SHA256. Every subsequent
host build can overwrite that DLL from the EKA source group. Restore and verify
**five** tested assets after each host build:

1. `avkonfep_general.dll` from the verified FEP build.
2. `mediaclientaudio_general.dll` from the verified MMF build.
3. `mediaclientvideo_v100.dll` from the verified MMF build.
4. `mediaclientaudio.dll.map` from the verified MMF build.
5. `mediaclientvideo.dll.map` from the verified MMF build.

The historical build/deployment hashes are in
`../../docs/validation-belle/fep-native-build/five-asset-identities.json`.
Validate a new build before changing those identities. No DLL or ELF is stored
with this recipe. Submit/empty Submit/Cancel, selection preservation, navigation,
focus/exit cancellation and the clipboard path require actual guest acceptance.
